# テストの書き方

## 書き方

- 画面と HTTP のふるまいを確かめるテストは `tests/Feature/` に、機能ごとに 1 ファイル（例: `ReplyTest.php`）で置きます。
- `RefreshDatabase` を使います。データは、その場でファクトリ（`User::factory()` など）で作ります。`DatabaseSeeder` の練習用データや、検証用アカウント（`usera@example.com` など）には頼りません。
- メソッド名は `test_` で始め、あとは日本語で「何をしたらどうなるか」を書きます（例: `test_他人のリプライは削除できない`）。
- URL は直接書かず `route()` で作ります。ログイン状態は `actingAs()` で作ります。
- 日付や順序が結果に関わるときは、`created_at` を明示します（`now()->subHour()` など）。

## 確かめること

- **認可**: 操作ごとに、「本人は成功する」「他人は 403 で、データも変わらない」「未ログインはログイン画面へ移動する」を確かめます。ポストの持ち主でも、他人のリプライは削除できない、のような「持ち主だからといって通らない」場合も確かめます。
- **ボタンの出し分け**: 画面のボタン（編集・削除など）が本人にだけ出ることを、`assertSee` / `assertDontSee` で確かめます。リンクや `action` は `route()` の結果で確かめ、HTML をエスケープしないよう第 2 引数に `false` を渡します。
- **入力チェック**: 必須と文字数は、境界の両側（140 字ちょうどは通る、141 字は通らない）を確かめます。エラーのときは、日本語のメッセージ（`assertSessionHasErrors` に文言を渡す）、元の画面へ戻ること、画面にエラーと入力途中の本文が出ること、データが増えないこと、の 4 つを確かめます。
- **データの結果**: 画面の表示だけでなく、`assertDatabaseHas` / `assertDatabaseCount` / `assertModelMissing` / `assertModelExists` で DB の状態も確かめます。親（ポスト・ユーザー）を消したときに子（リプライ）が消えるかも、ここで確かめます。
- **既存の画面**: 機能を足したとき、一覧など既存の画面が今までどおり動くことも 1 本は確かめます。
- **存在しない ID**: 詳細画面などは、存在しない ID で 404 になることを確かめます。
