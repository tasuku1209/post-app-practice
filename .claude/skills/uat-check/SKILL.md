# 要件確認と証跡（スクリーンショット）

要件を 1 つずつ画面で確かめて、判定と理由を、証拠のスクリーンショットとあわせて報告するための手順です。目的は「満たしているかどうかを、あとから第三者が見直せる形で残す」ことです。コードは直さず、直し方の提案も求められない限り書きません。

## 0. 準備

- 確認する要件を、1 行ずつの一覧にします。ユーザーが列挙していればそのまま使います。無ければ、設計書（`docs/*.md`）かイシューの受け入れ条件から拾い、**拾った一覧を最初に見せます**。
- アプリが動いているか確かめます（`curl -s -o /dev/null -w "%{http_code}" http://localhost/`）。動いていなければ `./vendor/bin/sail up -d` を提案します（勝手に起動しない）。
- Playwright のツールは遅延読み込みです。使う前に ToolSearch で、`navigate`・`snapshot`・`click`・`type`・`fill_form`・`take_screenshot`・`wait_for`・`evaluate` をまとめて読み込みます。
- ログインには検証用アカウント `usera@example.com` / `userb@example.com`（パスワードは `password`）を使います。**メールアドレスとパスワードは変えません**（`CLAUDE.md`）。投稿者本人と他人で動きが変わる要件は、この 2 つを切り替えて確かめます。
- 操作の前に、DB の状態を控えます（例: `./vendor/bin/sail artisan tinker --execute='echo App\Models\Reply::count();'`）。「増えた・増えない」は、画面だけでなく DB でも裏取りするためです。

## 1. 操作が効いたかを毎回確かめる（最重要）

**操作したことと、操作が効いたことは別です。** 次の順で、効いたことを確かめてから先へ進みます。

1. 操作の直後に、画面の変化を確かめる（`wait_for` で出るはずの文言を待つ、`snapshot` で URL と内容を見る）。
2. DB が関わる操作（登録・削除）は、DB の件数や中身でも確かめる。
3. 変化が無いときは、**スクリーンショットを撮って「成功」と書かない。** 先に原因を調べる。

### 送信やクリックが効かないとき

Chrome の「パスワードを変更してください」といったブラウザ本体のポップアップが出ていると、**ページの外にあるので、スナップショットにもスクリーンショットにも写らず**、通常のクリックだけが効かなくなることがあります（検証用のパスワードが `password` なので出やすい）。次の順で対処します。

1. ページ側の原因を切り分ける（フォームの `action`・`@csrf`・ボタンの `disabled`・ボタンの位置にいちばん手前にある要素を `evaluate` で調べる）。ページ側に問題が無く、通常のクリックだけ効かないなら、ブラウザ側を疑う。
2. ユーザーに「ブラウザにポップアップが出ていたら、OK で閉じてください」と頼む。閉じてもらえたら、通常のクリックで再度試す。
3. 閉じてもらえないときは、`evaluate` で DOM の `click()` を呼んで操作してよい。ただし、**報告に必ず書く**（どの操作を DOM の `click()` で行ったか、人がマウスで押したときも同じ動きかは確かめられていないこと）。

効かなかった試行の画像を、証跡として残しません（手順 2 の命名どおり、効いた結果だけを残す）。

## 2. スクリーンショット

- 保存先は、プロジェクト直下の `uat-shots/` です（無ければ作る）。`filename` に `uat-shots/...` を指定して、`fullPage: true` で撮ります。
- 名前は **`<要件の番号>-<何の証拠か>-<ユーザー>.png`** にします。要件ごとに分かるようにするためです。
  - 例: `02-reply-added-usera.png`、`04b-others-reply-no-delete-userb.png`
  - 1 つの要件に複数枚あるときは、`04a`・`04b` のように英小文字を足す。
- 撮るのは、**確かめたい結果が画面に出た状態**です。操作の前の画面や、反映前の画面を撮らない。
- 「ない」ことが要件のとき（他人のリプライに削除ボタンが出ない、など）は、**何がないのかが画面で分かるもの**を撮る。ログイン中のユーザーが写っている（ヘッダーが入る）ことを確かめる。
- 撮ったら、画像を `Read` で開いて、狙った内容が写っていることを自分の目で確かめる。

## 3. 判定

要件 1 つにつき、次の 3 つのどれかを付けます。

| 判定 | 使うとき |
|:--|:--|
| 満たしている | 画面で結果を確かめ、DB が関わる要件は DB でも裏取りした |
| 満たしていない | 画面または DB の結果が、要件と食い違った。何がどう違ったかを書く |
| 確かめられない | 操作できなかった、必要なデータが無かった、など。何が足りないかを書く |

- 推測で「満たしている」にしません。画面で見ていないことは、見ていないと書きます。
- 認可の要件（他人は消せない）は、**ボタンが出ないこと**だけでなく、**直接リクエストしたときに拒否されること**（403）も確かめる。画面の出し分けだけだと、Policy が効いている証明にならないからです。
- 空欄など入力チェックの要件は、エラー文言が出たことに加えて、**DB に増えていないこと**を確かめる。

## 4. 報告の形式

要件を 1 行ずつ、表で報告します。

```
# / 判定 / 理由（何を操作して、何が見えたか） / 証拠のファイル名
```

そのあとに、次を分けて書きます。

- **操作で例外的にしたこと**: DOM の `click()` を使った箇所など、通常の操作と違うことをしたとき。
- **DB に残ったもの**: 確認のために作ったデータ（テスト用のリプライなど）で、削除していないもの。
- **未コミットのもの**: `uat-shots/` と `.playwright-mcp/`。**勝手にコミットしない**（コミットするかはユーザーに聞く）。

## やらないこと

- コードの修正、コミット、プッシュ、PR へのコメント投稿。
- 検証用アカウントのメールアドレス・パスワードの変更（`CLAUDE.md`）。
- `answers/` の読み込み（`CLAUDE.md`）。
- 操作が効いたか確かめずに、スクリーンショットを撮って「満たしている」と書くこと。
- 効かなかった操作を、報告に書かずに別の方法に切り替えること。
