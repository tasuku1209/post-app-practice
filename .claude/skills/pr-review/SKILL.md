# PR レビュー（設計書との突き合わせ）

PR の差分を読んで、判定を報告するための手順です。目的は「直す」ことではなく、**人が見るべき場所を絞って3つまで渡す**ことです。そのため、コードは直さず、直し方の提案も求められない限り書きません。

## 0. 対象の PR を決める

`gh pr list --state all --limit 10` を実行します。

- ユーザーが番号を書いていないとき、または `<番号>` のような空欄のままのとき: PR が 1 件ならそれを対象にし、**報告の冒頭に「PR #N を対象にした」と書く**。2 件以上あるときは、勝手に選ばず聞く。
- マージ済みの PR でも、読めるなら読んでよい（その場合は「マージ済み」と添える）。
- 差分は `gh pr diff <番号>` で取る。長いときは scratchpad に保存して、必要な範囲だけ読む。

## 1. 設計書と突き合わせる

`docs/` の該当する設計書（例: `docs/reply.md`）を読み、差分と照らします。見るのは次の 2 点です。

- 設計書に書いていないものが増えていないか。**`composer.json`・`composer.lock` は特に注意**する。変更ファイル一覧（`gh pr view <番号> --json files`）にあるかで判定できる。パッケージが増えていれば、それだけで「要確認」。
- 受け入れ条件とテスト観点が、テストに 1 対 1 で対応しているか。

設計書の「変えないもの」の節が、次の手順 2 の対象になります。

## 2. 触っていないはずの場所を見る

設計書の「変えないもの」と「既存画面の変更」から、触っていないはずのファイルを挙げます。ルート、既存の Controller、既存の Policy、既存の画面が典型です。

**消えた行から先に見る。** 追加行は「足したいもの」なので疑いにくく、消えた行にこそ意図しない変更が混ざるからです。

- ファイルごとに、消えた行（`-` で始まる行）だけを取り出して読む。
- 消えた行が多いときは `git diff -w <base> <head> -- <file>` で、空白を無視した差分を見る。再インデントだけなら、そう書く。
- 差分が 0 行のファイルは「差分なし」と書く。
- 「触っていないはず」の前提が崩れているファイルは、設計書のどこに書いてある変更かを添える（設計書にあれば OK、なければ要確認）。

## 3. 中身を読む

次の観点で、追加されたコードを読みます。

| 観点 | 見るところ |
|:--|:--|
| N+1 | 一覧・詳細で、`with()` や `load()` が足りているか。Blade の中で関連を辿っていないか。件数の上限（ページ分け）が無いことも書く |
| 認可の置き場所 | 操作ごとに Controller で `$this->authorize()`、画面は `@can`。このプロジェクトでは条件を Controller や Blade に直接書かない（`CLAUDE.md`） |
| マスアサインメント | `create()` / `update()` に `$request->all()` を渡していないか。`user_id` を画面の入力から受けていないか。`$fillable` に余計な列が無いか |
| XSS | Blade の `{!! !!}` の有無。`style` 属性や `href` にユーザー入力が入っていないか |
| CSRF | `<form method="POST">` に `@csrf`、PUT / DELETE に `@method` があるか。ルートが `web` グループか |
| 入力チェック | ルールとメッセージが設計書の表と一致するか。`CLAUDE.md` の方針どおり Controller 内に書いているか（FormRequest は使わない）。境界値のテストがあるか |
| 書き方の揃い | 既存のコードと、コメント・命名・マイグレーションの流儀が揃っているか。既存画面からのコピー（重複）が無いか |

裏取りできるものは裏取りします（`grep` で `{!!` を探す、ミドルウェアの `TrimStrings` を確かめる、など）。推測で OK と書かないでください。

## 4. 報告の形式

1 観点につき 1 行で、次の順に書きます。

```
観点 / 判定 / ファイル名:行番号 / 気づいたこと
```

- 判定は **要確認・OK・対象外** の 3 つだけ。
- 行番号は、いまのブランチ（マージ済みなら main）のものを使う。
- **判定できないとき**は、何が足りないかを書く。たとえば `sail test` や `sail pint` を実行していなければ、「実行していないので判定できない」と書く。通ったことにしない。実行できないときは、読み取り専用の範囲で何を確かめたかも添える。
- 手順 1 → 2 → 3 の順に見出しを分けて書く。

最後に **「人が自分の目で読むべき場所」を 3 つまで**挙げます。選ぶ基準は、コードの正誤よりも、人の判断が要るところ（方針・見た目・認可の中心）を優先することです。3 つを超えて並べると、絞った意味がなくなります。

## やらないこと

- コードの修正、コミット、PR へのコメント投稿。依頼されていない外向きの操作は、確認なしにしない。
- `answers/` の読み込み（`CLAUDE.md` の指示）。
- 判定できないものを、推測で OK にすること。
